Agent Readiness of Major APIs: What the Open Data Actually Says

Published 24 September 2026. All figures below are recomputed from a single published dataset release, named at the end so you can check every number yourself.

Three findings, up front.

  • 21 of 25 API profiles are “constrained” — an agent can call the service, but cannot reliably finish its lifecycle unaided.
  • Exactly one service is fully agent-ready (grade A+, outcome pass), and it is a public DNS resolver, not a commercial platform.
  • Two carry grade D and outcome fail — the two that agents are most likely to be pointed at for repository and error-tracking work.

Why “the API works” is the wrong test

Most teams judge an API by whether a script can get a 200 back. That test passes almost everywhere and tells you almost nothing. The interesting question is the one an autonomous agent has to answer on its own, with no human in the loop:

“Given only public documentation and my own credentials, can I discover this service, sign up, understand what I will be charged, provision it, and handle its failure modes — without a human filling a gap?”

That question decomposes into five stages. Each stage is scored on its own, and a service can be excellent at one and blocked at the next. The five stages are:

  1. Evaluate — can an agent find the exact service and its stable entry points?
  2. Sign up — is there a stable route to begin obtaining access?
  3. Pay — is the commercial commitment disclosed before authorization, in machine-readable form?
  4. Provision — can the agent determine that provisioning actually completed?
  5. Operate — are the failure modes documented well enough to fail safely?

The pattern that emerges from the data is specific and worth stating plainly: APIs tend to score well on the first two stages and poorly on the last three. Discovery and sign-up are web problems, and the web solved them years ago. Payment disclosure, completion semantics and failure contracts are protocol problems, and they are largely unsolved.

The two failures, and the one clean pass

The extremes are more instructive than the middle. The only profile in the entire release that passes every stage is Cloudflare’s public 1.1.1.1 DNS resolver. That is not a coincidence and it is not a compliment to Cloudflare’s platform team: a DNS resolver has no account, no billing, no quota negotiation and no provisioning step. Four of the five stages do not exist for it. It is agent-ready because there is nothing to be ready for.

The two profiles that fail outright are Sentry’s Web API and GitHub Enterprise Server 3.21, both grade D. These are the uncomfortable ones. A repository API and an error-tracking API are exactly what an autonomous agent is most often pointed at — write code, open a PR, file and triage issues. The dataset says an agent cannot complete the lifecycle on either without a human stepping in at a stage that the task did not budget for.

The remaining 22 profiles sit in the wide middle, labelled limited. That word is doing a lot of work. It is not a synonym for “bad”; it means there is a condition attached, and the agent has to detect it by reading documentation rather than by reading a status field. Conditions that live only in prose are the ones agents miss.

Where the constraints actually cluster

Because each profile carries a per-stage finding, the aggregate can be read as a map of which stage tends to break rather than just how many services break. Two signals recur far more than any other across the dataset:

  • Pricing decidability. The condition is whether an agent can estimate cost, or confirm no-charge status, before it authorizes anything. Free tiers and trial credits are routinely described on a marketing page and absent from any machine-readable surface. An agent cannot read a marketing page and reliably decide whether it is about to spend money.
  • Provisioning completion. The condition is whether the agent can determine that a resource was actually created. An asynchronous 202 with no terminal state and no reconciliation route leaves the agent unable to tell success from a job still running — so it either waits forever or proceeds on an assumption.

Both are the same underlying failure: a fact the service knows, expressed in a channel the agent cannot read. Neither is hard to fix, and neither is fixed, because the humans who can read the marketing page never notice the gap.

What this means if you are building agents

Three practical consequences, in order of how much they cost you:

  • Budget the human step explicitly. If a target API is constrained, the integration is not “call the API”. Someone will sign up, accept terms, or unblock a provisioning step. If your plan does not name who, it is not a plan.
  • Treat pricing as unknown until machine-readable. Do not let an agent infer spend from documentation prose. If the commitment is not in a structured field, the correct behaviour is to stop, not to guess.
  • Prefer services that expose failure contracts. The difference between a retry loop and a duplicate-charge incident is whether the service tells you what a failed call means. A 5xx with a documented retry-safe semantics is worth more than a prettier SDK.
